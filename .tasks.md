We are developing a Mount & Blade II Bannerlord mod.

Mod name:

  Both Perks

Rules:

- Do not edit or add to `MB_source`; it is decompiled reference material.
- Keep Workshop packages clean: no source, no PDBs, no stale DLLs.
- Build/runtime paths are configured through `ModPaths.local.psd1`.
- **Never write mod data into save files.** No `[SaveableClass]`/`[SaveableField]` types, no
  payload in `BothPerksBehavior.SyncData`, no save reading/writing/migration. A save must stay
  loadable and uncorrupted if the mod is removed or downgraded. Per-campaign state is rebuilt in
  memory each session. Perks granted through `HeroDeveloper.AddPerk` land in vanilla hero data —
  that is the feature, not mod data, and is fine.

Current compatibility layout:

- `BothPerks.Bootstrap.dll` is loaded by `SubModule.xml`.
- The bootstrap chooses `compat\v1_2\BothPerks.Core.dll` for Bannerlord 1.2.x.
- The bootstrap chooses `compat\v1_3\BothPerks.Core.dll` for Bannerlord 1.3+.

Current installed reference versions:

- v1_2: `D:\BANNERLORDS\Mount & Blade II Bannerlord`
- v1_3: `D:\BANNERLORDS\Mount & Blade II Bannerlord1.3.15`

Functionality:

- Lets in-scope heroes receive both perks where they qualify.
- Supports manual, auto, and freedom modes through MCM.
- Applies Harmony UI patches for perk selection behavior.
- Adds an XP model for the optional skill XP multiplier.

If anything about version routing or packaging is unclear, ask before changing the release shape.

## Open bug: auto-assign does not keep working

Symptom: with mode = Auto, perks stop being granted as skills level up. Most visible on a newly
created campaign. Reported on game v1.4.7.

Ruled out during the 2026-07-25/26 investigation — do not re-investigate these:

- Not a 1.4.7 API break. Rebuilding `src\BothPerks.csproj` with `BannerlordTarget=v1_4` against
  the live 1.4.7 install compiles clean, and the result differs from the shipped Workshop DLL in
  exactly 72 bytes: PE timestamp, MVID, PDB debug-directory entry. Decompiled C# and the assembly
  reference table are identical.
- Not a game-side change. Full ILSpy diff of `TaleWorlds.CampaignSystem` 1.4.6 -> 1.4.7: 51 of
  1207 files differ, none of them `HeroDeveloper`, `PerkObject`, `CampaignEvents`,
  `CampaignEventDispatcher`, `Campaign` or `CampaignBehaviorManager`. `ViewModelCollection`:
  5 files differ, none perk-related. Every reflected member the mod uses still exists unchanged.
- Not the bootstrap. `Configs\ModLogs` confirms `[BothPerks] Loaded v1_4 core for v1.4.7.117484.`
- Not settings. `BothPerksSettings_v1.json` reads mode 1 (Auto), scope 1; MCM registers fine.

Root causes (both in our own code):

1. New-campaign attach ordering. `Campaign.cs` calls `GameManager.OnGameStart` (line ~1391), then
   snapshots the behavior list with `new CampaignBehaviorManager(starter.CampaignBehaviors)`
   (line ~1422, `SetBehaviors` does `.ToList()`). `MBSubModuleBase.OnNewGameCreated` fires much
   later, inside `Campaign.OnNewGameCreated` -> after `CampaignBehaviorManager.RegisterEvents()`
   has already run. So on a new campaign `CoreModule.TryAddBehavior` adds an orphan instance to a
   dead list, and on the way there its `RemoveStaleGameStateListeners()` (keep = null) unregisters
   the *working* instance's `GameStateManager` listener, permanently killing the
   `OnPushState` -> `RefreshPlayerClanPerks` character-screen sweep for that campaign.
   Saved games escape this only by accident: `GameManager.OnGameLoaded` fires at line ~1427, one
   line before the snapshot at ~1428.
2. Static caches outlive the campaign. `BothPerksBehavior._perksBySkill` and `_doctorsOathPerk`
   are `static`, but `PerkObject.All` is `Campaign.Current.AllPerks` and `Skills.All` is
   `Campaign.Current.AllSkills` — rebuilt per `Game`. `MBObjectBase` overrides `GetHashCode()`
   but not `Equals`, so the dictionary falls back to reference equality and every lookup misses
   for the second and later campaigns in one process. `GrantPerksForSkill` then returns silently
   and the on-skill-up grant never fires.

## TODO (approved, blocked by the hold above)

- [ ] Attach the behavior only in `CoreModule.OnGameStart`. That runs before the snapshot on both
      the new-campaign and saved-campaign paths, so it is sufficient on its own. Reduce
      `OnGameLoaded` / `OnNewGameCreated` to a fallback that attaches *via*
      `Campaign.Current.CampaignBehaviorManager` (which calls `RegisterEvents` immediately) and
      only when nothing is attached yet.
- [ ] Remove the `BothPerksBehavior.RemoveStaleGameStateListeners()` (keep = null) call from
      `CoreModule.TryAddBehavior`. `RegisterEvents` already does the targeted
      `RemoveStaleGameStateListeners(this)`, which is the correct form.
- [ ] Move `_perksBySkill` and `_doctorsOathPerk` from `static` to instance fields so they die
      with the campaign. Keeps state out of saves, per the rule above.
- [ ] Replace `Debug.Print` with `Trace.WriteLine` throughout the core. `Debug.Print` does not
      reach `Configs\ModLogs` in this setup, which is why every failure so far has been silent;
      the bootstrap's `Trace.WriteLine` lines do come through.

Verification once unblocked: start a new campaign, level a skill, confirm the perk is granted
without opening the character screen. Then quit to menu, load a save, level a skill again — that
second campaign in the same process is what the static-cache fix targets. Note that the launcher
currently has `both_perks_local` disabled and Workshop `both_perks` enabled, so a local rebuild
is not what the game loads unless that is flipped.
